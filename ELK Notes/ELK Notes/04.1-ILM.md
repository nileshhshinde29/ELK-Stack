### ILM Phases
#### Hot phase:
  - The highly required and frequently accessed data is stored in hot phase.
  - We can get data from this phase very fast.
  - It is recommended atleast one hr keep your data in Hot phase
  - This data is stored in SSD or NVMe.

#### Worm phase:
  - The less active data is stored in hot phase.
  - This stores data in SSD/ HDD
#### Cold Phase:
  - Rarely accessed data is stored in this phase.
  - I is used to lower the storage cost.
  - This data is stored in lower cost storage.  
#### Frozen:
  - Old but searchable data stored in this phase.
  - Generally searchable snapshots are stored
  - Stored in snapshot repo like S3 bucket.
#### Delete
  - In this phase data is deleted and can not be restored again.
  - There is also option to delete snapshot or not.

#### Imp
  - cold phase acn have searchable snapshot where hot phase not
  - Replica remains same ase per previous phase by default.
  - In Frozen zone data is stored in snapshot repository but elastic search required local information/catch for searching. 
    So it need to be configured. It provides low-cost storage for old data.

### ILM Actions

#### rollover
- create new index.

#### readonly:
- make index read-only. 
- so no new data added.
- Existing data can still be searched.

#### shrink
- Reduces primary shards
- useful when old data doesn't need many shard

#### forcemerge
- Merge the lucene segment

#### migrate
- migrate data to appropriate tier
- Hot → Warm → Cold.


#### searchable_snapshot
- Allows data to be searched directly from a snapshot.

#### set_priority
- Controls recovery priority
- Higher-priority indices can be recovered before lower-priority ones.

###  Downsampling
Reduces the granularity of older time-series data.

Example:

```text
10-second data
      ↓
1-minute data
      ↓
5-minute data
```
This reduces storage usage while keeping useful historical information.

# Elasticsearch ILM – Interview Notes

## 1. What is ILM, why do we need it, and how does it work?

**ILM (Index Lifecycle Management)** automatically manages Elasticsearch indices as data gets older.

Typical lifecycle:

```text
HOT → WARM → COLD → FROZEN → DELETE
```

ILM helps with:

* Index rollover
* Data tier movement
* Data optimization
* Storage management
* Retention
* Automatic deletion

### Why do we need ILM?

Without ILM:

* Indices keep growing
* Storage usage increases
* Large indices become difficult to manage
* Manual cleanup is required
* Storage costs can increase
* Search/indexing performance can be affected

---

# 12. What are common ILM problems and best practices?

## Common Problems

* Too many small shards
* Extremely large indices
* Using only age-based rollover
* Incorrect tier allocation
* Too many replicas on old data
* Missing snapshot repository
* Not monitoring ILM
* Not testing the ILM policy

## Best Practices

* Use **size + age based rollover**
* Keep shard sizes reasonable
* Move old data to cheaper storage
* Downsample older metrics when appropriate
* Monitor ILM regularly
* Test snapshot and restore procedures
* Test ILM policies before production
* Set retention based on business and compliance requirements
