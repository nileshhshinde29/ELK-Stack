# Elasticsearch Alerting – Interview Notes

## 1. What is Alerting, why is it important, and how does it work?

Alerting means **continuously checking Elasticsearch/Kibana data for a specific condition** and taking an action when that condition becomes true.

Examples:

```text
CPU > 80%
Server Status = DOWN
Error Count >= 10
```

### Why is Alerting important?

* Detect issues automatically
* Get real-time notifications
* Monitor application and server performance
* Detect security issues
* Take action before the problem becomes bigger

Basic flow:

```text
Data
 ↓
Rule
 ↓
Condition
 ↓
Action
 ↓
Email / Slack / Incident
```

> **Monitoring tells us what is happening, while Alerting tells us when we need to take action.**

### Important Alerting Terms

**Rule** → Defines what we want to monitor.

**Condition** → Defines when the alert should trigger.

**Schedule** → Defines how frequently the rule checks.

**Action** → Defines what should happen when the condition is true.

**Connector** → Connects Kibana Alerting with an external service.

Example:

```text
Rule       → Monitor CPU
Condition  → CPU > 80%
Schedule   → Every 1 minute
Action     → Send Email
Connector  → Email
```

# 2. What are Connectors and why are they used?

Connectors connect **Kibana Alerting with external services** so that alert notifications can be sent to the appropriate platform.

Example:

```text
Kibana
  ↓
Email Connector
  ↓
SMTP / Email
```

or:

```text
Kibana
  ↓
Slack Connector
  ↓
Slack Channel
```

### Common Connectors

* Email
* Slack
* Microsoft Teams
* PagerDuty
* Jira
* ServiceNow
* Webhook
* Index
* Server Log

Different teams can use different connectors.

```text
Email     → Formal notification
Slack     → Team notification
PagerDuty → On-call alert
Jira      → Create ticket
Webhook   → Custom integration
```

The exact connector availability can depend on the Elastic version and configuration.

# 3. How do you create a Server Down Alert using Heartbeat?

Suppose we want an alert when a website/server goes DOWN.

We can use Heartbeat data:

```text
Data → heartbeat-*
```

Filter:

```text
monitor.status: "down"
```

Condition:

```text
Count >= 1
```

Schedule:

```text
Every 1 minute
```

Action:

```text
Send Email / Slack
```

### Alert Flow

```text
Server goes DOWN
       ↓
Heartbeat detects failure
       ↓
Rule checks condition
       ↓
Condition = TRUE
       ↓
Action executes
       ↓
Email / Slack notification
```

### Example

```text
Rule Name → Server Down Alert
Data      → heartbeat-*
Filter    → monitor.status: "down"
Condition → Count >= 1
Schedule  → Every 1 minute
Action    → Email
Tags      → production, heartbeat
```

# 4. What is Custom Threshold Alerting?

Custom Threshold allows us to define our own **metric or log limit** and generate an alert when the value crosses that limit.

Examples:

```text
CPU > 80%
Memory > 90%
Error Count > 100
Response Time > 2 seconds
```

We can also define a time period:

```text
Last 5 minutes
```

Simple definition:

> **Custom Threshold = Define a limit and alert when the value crosses that limit.**

It can be used with relevant **logs, metrics, and APM data**.

# 5. What is Watcher and how is it different from Kibana Alerting?

## Watcher

Watcher is a **JSON/API-based alerting mechanism** in Elasticsearch.

It is useful when we need:

* Complex queries
* Aggregations
* Scripts
* Custom conditions
* Custom actions
* Webhooks

## Kibana Alerting

Kibana Alerting allows us to create rules using the **Kibana UI**.

We can configure:

```text
Rule Type
   ↓
Condition
   ↓
Schedule
   ↓
Action
```

### Difference

```text
Watcher
→ JSON / API
→ More customized logic

Kibana Alerting
→ UI-based
→ Easier for standard alerting
```

Simple way to remember:

> **Kibana Alerting = UI-based alerting**

> **Watcher = JSON/API-based alerting**

# 6. What are the main components of Watcher?

Watcher has four main components:

```text
TRIGGER
INPUT
CONDITION
ACTION
```

### 1. Trigger

Defines **WHEN** the Watcher should run.

Example:

```json
"trigger": {
  "schedule": {
    "interval": "15m"
  }
}
```

This means:

```text
Run every 15 minutes.
```

Common schedules:

```text
30s
15m
1h
Cron
```

### 2. Input

Defines **WHAT DATA** the Watcher should check.

Example:

```text
Index  → heartbeat-*
Query  → monitor.status: "down"
Time   → Last 15 minutes
Size   → 10
Sort   → Latest first
```

Important Input parts:

```text
indices
query
_source
size
sort
```

### 3. Condition

Defines **WHETHER the alert should trigger**.

Example:

```text
Down events >= 1
```

If the condition is TRUE, the action executes.

Watcher result data can be accessed using:

```text
ctx.payload
```

Common condition types:

```text
Compare
Script
```

### 4. Action

Defines **WHAT SHOULD HAPPEN** when the condition is TRUE.

Examples:

```text
Send Email
Write Log
Send Notification
Webhook
```

### Easy Way to Remember

```text
Trigger   → WHEN?
Input     → WHAT DATA?
Condition → SHOULD ALERT?
Action    → WHAT TO DO?
```

# 8. How do you configure Email Alerting?

Basic process:

```text
1. Configure Kibana encryption keys
          ↓
2. Create Gmail App Password
          ↓
3. Configure SMTP
          ↓
4. Store credentials securely
          ↓
5. Check license/features
          ↓
6. Create Email Connector
          ↓
7. Test Connector
          ↓
8. Attach Connector to Rule
```

### Gmail SMTP Example

```text
SMTP Host → smtp.gmail.com
Port      → 587
STARTTLS  → Enabled
Auth      → Enabled
```

For Gmail, use an **App Password** where required instead of the normal account password.

### Security

Do not:

```text
Hardcode passwords
Commit passwords to Git
Expose SMTP credentials
```

Store sensitive credentials securely, such as using the appropriate **keystore/secret configuration**.

After creating the connector:

```text
Stack Management
    ↓
Connectors
    ↓
Create Connector
    ↓
Email
    ↓
Test
```

Then attach the connector to the alert rule.

# 9. What are the best practices for Elasticsearch Alerting?

Important practices:

### Use an appropriate schedule

```text
Schedule → Every 5 minutes
Query    → Appropriate recent time window
```

The query window should match the rule's execution frequency.

### Use throttling

Prevents repeated notifications for the same ongoing problem.

```text
Problem continues
      ↓
Rule keeps running
      ↓
Throttle prevents duplicate alerts
```

### Keep queries efficient

* Use filter clauses when scoring is unnecessary
* Return only required fields
* Avoid unnecessarily large result sizes
* Test queries before production

### Secure credentials

* Don't hardcode passwords
* Don't commit secrets to Git
* Use secure credential storage

### Test before production

```text
Test Query
   ↓
Test Condition
   ↓
Test Connector
   ↓
Test Alert
   ↓
Production
```
