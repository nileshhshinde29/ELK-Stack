### ILM Phases
#### Hot phase:
  - The highly required and frequently accessed data is stored in hot phase.
  - We can get data from this phase very fast.
  - It is recommended atleast one hr keep your data in Hot phase
  - This data is stored in SSD or NVMe.

#### Worm phase:
  - The less active data is stored in hot phase.
  - This stores data in SSD/ HDD
#### Cold Phase:
  - Rarely accessed data is stored in this phase.
  - I is used to lower the storage cost.
  - This data is stored in lower cost storage.  
#### Frozen:
  - Old but searchable data stored in this phase.
  - Generally searchable snapshots are stored
  - Stored in snapshot repo like S3 bucket.
#### Delete
  - In this phase data is deleted and can not be restored again.
  - There is also option to delete snapshot or not.

#### Imp

  - Replica remains same ase per previous phase by default.
  - In Frozen zone data is stored in snapshot repository but elastic search required local information/catch for searching. 
    So it need to be configured. It provides low-cost storage for old data.

# Elasticsearch ILM – Interview Notes

## 1. What is ILM, why do we need it, and how does it work?

**ILM (Index Lifecycle Management)** automatically manages Elasticsearch indices as data gets older.

Typical lifecycle:

```text
HOT → WARM → COLD → FROZEN → DELETE
```

ILM helps with:

* Index rollover
* Data tier movement
* Data optimization
* Storage management
* Retention
* Automatic deletion

### Why do we need ILM?

Without ILM:

* Indices keep growing
* Storage usage increases
* Large indices become difficult to manage
* Manual cleanup is required
* Storage costs can increase
* Search/indexing performance can be affected

With ILM:

```text
New Data
   ↓
Fast Storage
   ↓
Older Data
   ↓
Cheaper Storage
   ↓
Expired Data
   ↓
Automatic Delete
```

> **Interview Answer:** ILM automates the complete lifecycle of Elasticsearch data from indexing to deletion.

---

# 2. What are the ILM phases?

The main ILM phases are:

| Phase  | Purpose                             | Typical Storage     |
| ------ | ----------------------------------- | ------------------- |
| HOT    | Active and frequently accessed data | SSD/NVMe            |
| WARM   | Older, less active data             | SSD/HDD             |
| COLD   | Rarely accessed data                | Lower-cost storage  |
| FROZEN | Very old but searchable data        | Snapshot repository |
| DELETE | Expired data                        | Removed             |

# 4. What is Rollover and how is it related to ILM?

**Rollover** means Elasticsearch starts writing to a **new index when configured limits are reached**.

Common rollover conditions:

```text
max_primary_shard_size
max_age
max_docs
```

Example:

```text
logs-000001
     |
     | 50 GB reached
     ↓
logs-000002
```

### Why use rollover?

It prevents a single index from becoming too large.

### Rollover vs ILM

**Rollover**:

```text
logs-000001
     ↓
logs-000002
     ↓
logs-000003
```

Creates a new index based on configured conditions.

**ILM**:

```text
Rollover
   ↓
HOT → WARM → COLD → FROZEN → DELETE
```

Manages the **complete lifecycle**.

> **Rollover is one part of ILM.**

---

# 5. What happens in the WARM phase?

**WARM = Older, less active data**

Data is accessed less frequently, so Elasticsearch can optimize it for storage and search.

Common actions:

```text
readonly
shrink
forcemerge
set_priority
downsampling
```

### Shrink

Reduces the number of primary shards.

Example:

```text
5 Primary Shards
       ↓
1 Primary Shard
```

### Forcemerge

Merges Lucene segments and can optimize older read-only indices.

### Downsampling

Reduces the granularity of older time-series data.

Example:

```text
10-second data
      ↓
1-minute data
      ↓
5-minute data
```

This reduces storage usage while keeping useful historical information.

---

# 6. What are the COLD and FROZEN phases?

## COLD Phase

**COLD = Rarely accessed data**

Characteristics:

* Older data
* Less frequent searches
* Lower-cost storage
* Lower performance requirement
* Can use cold-tier nodes

> **COLD focuses on storing rarely accessed data at a lower cost.**

## FROZEN Phase

**FROZEN = Very old but still searchable data**

Frozen data can use **searchable snapshots**.

Most data remains in the snapshot repository, while Elasticsearch uses the required local information/cache for searching.

A snapshot repository needs to be configured before using searchable snapshots.

> **FROZEN provides low-cost storage while keeping old data searchable.**

# 8. What are Index Templates, Bootstrap Index, and Rollover Alias?

These are important when configuring **ILM with rollover**.

## Index Template

An index template applies settings to newly created indices.

It can connect:

```text
Index Pattern
+
ILM Policy
+
Rollover Alias
```

Example:

```json
PUT _index_template/logs_template
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "logs_policy",
      "index.lifecycle.rollover_alias": "logs"
    }
  }
}
```

## Bootstrap Index

Before rollover starts, the first index must be created.

This is called the **bootstrap index**.

Example:

```json
PUT logs-000001
{
  "aliases": {
    "logs": {
      "is_write_index": true
    }
  }
}
```

Applications write to:

```text
logs
```

instead of directly writing to:

```text
logs-000001
```

Then rollover can create:

```text
logs-000002
logs-000003
logs-000004
```

### Easy way to remember

```text
Index Template
      ↓
ILM Policy + Rollover Alias
      ↓
Bootstrap Index
      ↓
Application writes to Alias
      ↓
Automatic Rollover
```

# 11. What is Downsampling and why is it used?

**Downsampling** is mainly used for **time-series data**.

It reduces the granularity of older data.

Example:

```text
10-second data
      ↓
1-minute data
      ↓
5-minute data
```

Instead of keeping every high-frequency data point, older data can be stored at a lower resolution.

Benefits:

* Reduces storage
* Reduces data volume
* Useful for older metrics
* Keeps historical trends available

> **Downsampling = Reduce time-series data granularity to save storage.**

# 12. What are common ILM problems and best practices?

## Common Problems

* Too many small shards
* Extremely large indices
* Using only age-based rollover
* Incorrect tier allocation
* Too many replicas on old data
* Missing snapshot repository
* Not monitoring ILM
* Not testing the ILM policy

## Best Practices

* Use **size + age based rollover**
* Keep shard sizes reasonable
* Move old data to cheaper storage
* Downsample older metrics when appropriate
* Monitor ILM regularly
* Test snapshot and restore procedures
* Test ILM policies before production
* Set retention based on business and compliance requirements
