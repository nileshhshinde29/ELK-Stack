# Elasticsearch Ingest Pipeline – All Processors Example

1. What is ingest pipeline?
- It is used to processes documents before indexing. We use it for parsing, enrichment, field cleanup, routing, and timestamp correction.
- It is good for light weight processing and when we have less fields to process.
- logstash is better for complex parsing and heavy transformation.

2. Pipeline works in Dev but not Prod. What do you check?
- Sample log difference, 
- field path difference, 
- index template, 
- pipeline assignment, 
- Fleet integration, 
- Logstash output, and failure processor.

## 1. Example: E-commerce Application Logs

**Input document:**

```json
{
  "message": "2026-10-23 10:30:00 ERROR payment Payment failed",
  "status_code": 500,
  "http_response_body": "Large response payload...",
  "app": "payment",
  "environment": "unknown"
}
```

## 2. common filters

```json
PUT _ingest/pipeline/ecommerce_pipeline
{
  "processors": [
    {
      "dissect": {
        // It is helpful when we have same pattern data.
        // It Splits the raw 'message' string into separate fields using a fixed delimiter pattern
        // It is faster than grok.
        "field": "message",
        "pattern": "%{log_time} %{log_level} %{service.name} %{error.message}"
      }
    },
    {
      "date": {
        // It Parses 'log_time' text into a real date and writes it to @timestamp (default target), using the given format and timezone
        "field": "log_time",
        "formats": ["yyyy-MM-dd HH:mm:ss"],
        "timezone": "Asia/Kolkata"
      }
    },
    {
      "rename": {
        // Renames 'status_code' to the ECS-standard field 'http.response.status_code'
        "field": "status_code",
        "target_field": "http.response.status_code"
      }
    },
    {
      "set": {
        // Adds (or overwrites) a field with a fixed value - here tags every document as production
        "field": "service.environment",
        "value": "production"
      }
    },
    {
      "script": {
        // Runs Painless code for custom logic - here adds a boolean 'is_server_error' = true when status code is 5xx
        "source": "ctx.is_server_error = ctx.http.response.status_code >= 500"
      }
    },
    {
      "remove": {
        // Deletes unwanted/temporary fields to save storage; ignore_missing avoids failure if a field is absent
        "field": [
          "http_response_body",
          "app",
          "environment",
          "log_time"
        ],
        "ignore_missing": true
      }
    },
    {
      "enrich": {
        // Looks up 'service.name' in the enrich index (app_owner_policy) and copies matching details (e.g. owner, team) into 'application_details'
        "policy_name": "app_owner_policy",
        "field": "service.name",
        "target_field": "application_details",
        "ignore_missing": true
      }
    }
  ]
}
```

## 4. Expected Output

```json
{
  "@timestamp": "2026-10-23T05:00:00Z",
  "log_level": "ERROR",
  "service": {
    "name": "payment",
    "environment": "production"
  },
  "error": {
    "message": "Payment failed"
  },
  "http": {
    "response": {
      "status_code": 500
    }
  },
  "is_server_error": true,
  "application_details": {
    "owner": "Finance Team"
  }
}
```

*Note: The enrichment output assumes the enrich policy contains a matching `payment` record. The policy must be created and executed before using the pipeline.*

## 5. Quick Revision

| Processor | Purpose | Example |
|---|---|---|
| Dissect | Splits fixed-format logs | Extract level and service |
| Date | Parses timestamps | Sets `@timestamp` |
| Rename | Renames fields | `status_code` → `http.response.status_code` |
| Set | Adds or updates values | `service.environment: production` |
| Script | Applies custom logic | Identifies server errors |
| Remove | Deletes unwanted fields | Removes large response body |
| Enrich | Adds lookup information | Adds application owner |
