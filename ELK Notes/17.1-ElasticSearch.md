### Q12. What is an alias?

- Alias is a logical name pointing to one or more indices.
- We use aliases to simplify search and support zero-downtime index switching.

**Example:** add one alias `all-app-logs` to two indices.

```json
POST _aliases
{
  "actions": [
    {
      "add": {
        "index": "logs-flipkart-prod",   // first index
        "alias": "all-app-logs"          // common alias name
      }
    },
    {
      "add": {
        "index": "logs-amazon-prod",     // second index
        "alias": "all-app-logs"          // same alias
      }
    }
  ]
}
```

- Now search on the alias, and it searches both indices:

```json
GET all-app-logs/_search
```

<a id="q14"></a>

### Q14. What is near real-time search? What is refresh interval? How refresh interval impacts performance?

- Elasticsearch is near real-time because documents are not searchable immediately after indexing.
- They become searchable after refresh, usually around 1 second by default.
- Refresh interval controls how frequently newly indexed documents become searchable.
- Refresh interval is added in index_template , by default its 1 sec
- Lower refresh interval: Data becomes searchable faster, but indexing can become slower.
- Higher refresh interval: Data takes longer to become searchable, but indexing can become faster.
- For heavy ingestion, I increase refresh interval to improve indexing performance.

<a id="q23"></a>

### Q23. Why are shards required?

- It is small part of index which stores the data.
- distribute data across multiple nodes and scale horizontally.

[⬆ Back to Q23 in list](#idx-q23)

<a id="q24"></a>

### Q24. How do replicas improve availability? What happens when a node fails, and what is shard recovery?

- If a node holding primary shard fails, replica shard can be promoted to primary.
- **Node failure:** Replica shards are promoted, cluster may turn yellow temporarily, and Elasticsearch starts shard recovery/reallocation.
- **Shard recovery:** Shard recovery is copying shard data from primary or snapshot to bring shard back online.

[⬆ Back to Q24 in list](#idx-q24)

<a id="q25"></a>

### Q25. How many shards should an index have, and why are too many or very large shards bad? How do you calculate shard size?

- **Shard count:** It depends on data volume. In log environments, I generally target shard size around 20–50 GB depending on retention, query pattern, and hardware.
- **Too many shards:** Too many shards increase cluster state, heap usage, search overhead, and recovery time. I always check shard count during performance troubleshooting.
- **Very large shards:** Large shards take longer to recover, relocate, and search. If one 200 GB shard fails, recovery takes much longer than smaller balanced shards.
- **Shard size:** Total index size divided by number of primary shards.
- Example: 500 GB index with 10 primary shards = around 50 GB per shard.

[⬆ Back to Q25 in list](#idx-q25)

<a id="q26"></a>

### Q26. What are shard allocation, relocation, and rebalancing? ( its automatically done by ES)

- **Allocation:** Shard allocation is the process where Elasticsearch decides which node should hold which shard.
- **Relocation:** Shard relocation means Elasticsearch moves a shard from one node to another for balancing or tier movement.
- **Rebalancing:** Rebalancing distributes shards evenly across nodes based on allocation rules, disk usage, and cluster balance.

[⬆ Back to Q26 in list](#idx-q26)

<a id="q27"></a>

### Q27. How do you troubleshoot unassigned shards? Why are shards unassigned? Node joined but shards not allocated. What is shard allocation explain API?  (_cluster/allocation/explain )

**Ans:** First run `_cluster/allocation/explain`. It tells exactly why a shard is unassigned or not moving to a node. Most important troubleshooting APIs. Common reasons:
- Node failure / insufficient nodes
- Disk watermark
- Node role mismatch
- Tier preference / tier mismatch
- Allocation rules / allocation filtering
- Shard limits per node
- Replica count
- Corrupt shard → snapshot recovery

[⬆ Back to Q27 in list](#idx-q27)

<a id="q28"></a>

### Q28. What is shard skew?

- data/shards are unevenly distributed.
- One node may hold too much data or too many heavy shards.

[⬆ Back to Q28 in list](#idx-q28)

<a id="q29"></a>

### Q29. What is yellow cluster health? Why cluster becomes yellow after adding replica? Cluster health yellow. What do you check? Cluster yellow for several days.

**Ans:** Primary shards are assigned but replica shards are unassigned. Check:
- Unassigned replicas: `_cat/shards`, `_cluster/allocation/explain`
- Number of nodes: a replica is never placed on the same node as its primary, so a single node stays yellow
- Replica count is higher than available nodes
- Disk watermark: node disk is too high, so new shards stop being allocated to that node
- Tier availability / tier preference: a hot replica is not assigned to a warm node by default
- Allocation filtering

[⬆ Back to Q29 in list](#idx-q29)

<a id="q30"></a>

### Q30. What is red cluster health? Why cluster becomes red after restart? Cluster health red. What do you check? Cluster red after node restart.

**Ans:** At least one primary shard is unassigned. Check:
- Missing primary shards: `_cluster/health`, `_cat/shards`
- Node rejoined or not / missing node
- `_cluster/allocation/explain`
- Disk issue
- Corrupt shard (restore from snapshot if needed)
- Allocation disabled (re-enable after restart)
- Recovery status

- [Learn about cluster](<./01.ELK%20Notes%201.md#cluster>)

### Q34. Difference between text and keyword? Match query vs term query?

### Q35. Why dashboards fail after field type change? Field is keyword in one index and text in another. What happens? Kibana dashboard stopped after mapping change. How do you fix mapping conflict?

**Ans:** If a field changes from keyword to text, Kibana shows a field conflict and aggregations fail, because text fields can't be used for terms aggregation unless fielddata is enabled. Check:
- Field type conflict
- Missing `.keyword`
- Lens field reference
- Data view refresh


   "type": "text",
   "fielddata": true  // for mapping we are adding filed data true, so text field also can be used for aggregation and sorting.


**Fix:** Using re-indexing. Fix the index template and reindex the affected indices.
- [Link](16.1-Kibana.md#4-fields-runtime-fields--scripted-fields)

## 14. Architect-Level Design
<a id="q82"></a>

### Q82. What is CCS? What is CCR? CCS vs CCR?

- Cross Cluster Search allows searching remote clusters from one cluster.
- Cross Cluster Replication replicates indices from leader cluster to follower cluster.

| CCS | CCR |
|---|---|
| CCS is for querying remote data. | CCR is for copying data to another cluster for DR or locality. |

**Example:**
समजा, Pune मध्ये तुझा Production Elasticsearch cluster आहे आणि Mumbai मध्ये दुसरा cluster आहे.
1. Pune च्या leader cluster मध्ये application logs येतात.
2. CCR ते logs Mumbai च्या follower cluster मध्ये replicate करते.
3. Pune cluster उपलब्ध नसल्यास, Mumbai cluster मधील replicated data वापरून search किंवा recovery करता येऊ शकते.

**CCR का वापरतात?**
- Disaster recovery
- दुसऱ्या location मधून data search करणे
- वेगवेगळ्या clusters मधील data ची प्रत ठेवणे

[⬆ Back to Q82 in list](#idx-q82)

<a id="q83"></a>

### Q83. How do you design DR in Elasticsearch? How do you design backup and recovery?

- DR म्हणजे Disaster Recovery. म्हणजे Production cluster बंद पडला किंवा data loss झाला, तर system पुन्हा सुरू करण्याची तयारी.
- सोप्या भाषेत, आपण Snapshots आणि CCR वापरतो.

**1. Snapshots for backup**
- Snapshots म्हणजे Elasticsearch च्या data चा backup.
- Snapshots S3 सारख्या repository मध्ये store करतो.
- Data delete झाला किंवा cluster fail झाला, तर snapshot restore करून data recover करू शकतो.
- Snapshots नियमितपणे schedule करतो.

**2. CCR for low RPO**
- CCR म्हणजे Cross-Cluster Replication.
- Leader cluster मधील indices follower cluster मध्ये replicate होतात.
- Primary cluster बंद पडल्यास follower cluster मधील replicated data वापरून recovery करता येऊ शकते.
- Replication asynchronous असल्यामुळे काही नवीन data replicate होण्यापूर्वी गमावला जाऊ शकतो.

**3. RPO आणि RTO स्पष्ट ठरवणे**

| Term | Full form | मराठी + English अर्थ | Example |
|---|---|---|---|
| **RPO** | Recovery Point Objective | किती data loss आपण tolerate करू शकतो. | 5 मिनिटांपर्यंतचा data loss acceptable आहे. |
| **RTO** | Recovery Time Objective | System पुन्हा किती वेळात सुरू झाला पाहिजे. | 30 मिनिटांच्या आत service सुरू झाली पाहिजे. |

**Example:**
समजा, Production cluster सकाळी 10:00 वाजता बंद पडला.
- **RPO = 5 minutes:** जास्तीत जास्त 5 मिनिटांचा data loss acceptable आहे.
- **RTO = 30 minutes:** सकाळी 10:30 पर्यंत service पुन्हा सुरू करण्याचे target आहे.

**4. Backup and recovery design**
- Automated SLM snapshots,
- repository verification,
- periodic restore testing,
- documented RTO/RPO,
- snapshot retention.

**Interview answer:**
> “I design Disaster Recovery using snapshots and CCR. Snapshots provide backup and recovery, while CCR maintains a replicated copy of data in another cluster. I define RPO and RTO based on business requirements, monitor replication lag, and regularly test snapshot restoration and DR failover.”

**लक्षात ठेव:**
- Snapshots = Backup
- CCR = Replication
- RPO = किती data loss चालेल?
- RTO = System पुन्हा सुरू व्हायला किती वेळ चालेल?

### Q108. Why aggregations are slow? How do you optimize aggregation?

**Why slow:**
- Large time range, high cardinality fields, too many shards, runtime fields, scripted fields, or missing keyword fields.

**Optimize:**
- Use keyword fields, reduce time range, reduce shard count, pre-aggregate data using transforms, avoid scripts/runtime fields.
