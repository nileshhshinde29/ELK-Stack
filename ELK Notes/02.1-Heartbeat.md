## 1. Heartbeat Overview

<a id="q1"></a>

### Q1. What is Elastic Heartbeat? What does Heartbeat allow us to monitor?

- **Lightweight monitoring tool (Beat)** → checks whether a service / application / API / server is **available or not**.
- Checks the target continuously and sends **availability, response time, status** to Elasticsearch.
- Data is visualized in the **Kibana Uptime** app.
- Can monitor:
  - Applications
  - APIs
  - Websites
  - Servers
  - Network services
- Checks can run from **different locations** → detect problems **before users report them**.

<a id="q2"></a>

### Q2. What are the problems with reactive monitoring? How is proactive monitoring with Heartbeat different? What is the outcome?

**Reactive monitoring (problem known after it happens)**

- Alert comes only after the service is down.
- Higher **MTTR (Mean Time to Recovery)**.
- No idea if users from another location are affected.
- Manual health checks take time.
- No real-time visibility into **SLA/SLO**.
- Customers sometimes find the issue before the support/engineering team.

**Proactive monitoring (Heartbeat)**

- Checks services continuously at a **fixed interval**.

```text
Every 10 seconds → Check the application
Every 30 seconds → Check the API
Every 1 minute  → Check the server
```

- Protocols → **HTTP/HTTPS, TCP, ICMP**

**Outcome**

- Detect problems early
- Reduce downtime and MTTR
- Improve service availability
- Find problems before customers report them

<a id="q3"></a>

### Q3. What are the core capabilities of Heartbeat? What is its key advantage? What is the Heartbeat architecture?

**Core capabilities**

- Monitors configured in **YAML**.
- Define target **host / URL** and check **frequency** (`schedule`).
- Configure **HTTP headers** and other options.
- Monitor **SSL/TLS certificates**.
- Add custom info → environment, location, tags.
- Send data **directly to Elasticsearch**.

**Key advantage**

- Sends data **directly to Elasticsearch** → **Logstash is not mandatory** for the basic pipeline.
- Results visualized in Kibana **Uptime** app.

**Architecture**

```text
Heartbeat
    ↓
Elasticsearch
    ↓
Kibana Uptime
    ↓
Alerts / Notifications
```

## 2. Monitor Types and Requirements

<a id="q4"></a>

### Q4. What types of monitoring can we perform with Heartbeat? What is the main rule? What does each monitor require?

**Main rule** → **Heartbeat must be able to directly reach the target system.**
If Heartbeat server cannot reach the target **IP / port / website** → monitor shows **DOWN**.

| Type | Used for | Checks | Requirement |
| --- | --- | --- | --- |
| **HTTP/HTTPS** | Websites, APIs | URL availability, status code, response body, SSL/TLS | URL reachable, DNS resolves, valid response within timeout |
| **TCP** | Port / service accepting connections | Connect to `host:port` (e.g. `localhost:9200`) | Server IP + port reachable |
| **ICMP** | Basic host / network connectivity | Reachability, latency, packet loss | IP reachable, firewall allows ICMP request + response |
| **TLS** | SSL/TLS certificates | Certificate validity and expiry | HTTPS endpoint reachable |

```text
TCP  → Database → 10.0.0.5:3306
HTTP → https://api.app.com → HTTP 200 OK
```

<a id="q5"></a>

### Q5. When do we use ICMP monitoring? What does ICMP configuration look like? What if ICMP monitoring doesn't work?

**When**

- To check **basic network / host availability** (ping).

```text
Server → Ping → Response
```

- Measures → network reachability, response time, packet loss.
- Does **NOT** check if the application is working → only that host/network is reachable.

**Configuration**

```yaml
heartbeat.monitors:

- type: icmp
  id: ping-public-dns
  name: "Public DNS"
  schedule: "@every 30s"
  hosts: ["8.8.8.8", "1.1.1.1"]
  timeout: 3s   # how long Heartbeat waits for a response
  mode: any     # any → at least one host should respond

- type: icmp
  id: ping-internal-gw
  name: "Internal Gateway"
  schedule: "@every 15s"
  hosts: ["10.0.0.1"]
  mode: all     # all → every configured host should respond
```

**ICMP not working?**

- ICMP needs permission to create **raw network sockets**.
- On Linux → run Heartbeat with required privileges, or give the capability:

```bash
sudo setcap cap_net_raw+eip /path/to/heartbeat
```

- So also check **permissions/capabilities of the Heartbeat process**.

<a id="q6"></a>

### Q6. What does TCP configuration look like? What is check.send / check.receive?

```yaml
heartbeat.monitors:

- type: tcp
  enabled: true
  id: localhost_Elastic
  name: "localhost_Elastic_URL"
  hosts: ["localhost:9200"]
  schedule: "@every 2m"
  check.send: "ping\n"   # Heartbeat sends "ping"
  check.receive: "pong"  # server should reply "pong"
```

- `check.send` → payload Heartbeat sends after connecting.
- `check.receive` → expected reply. Received → check **passes**; not received → check **fails**.
- Without `check.send/receive` → only verifies the port accepts a connection.

<a id="q7"></a>

### Q7. What does HTTP/HTTPS configuration look like? What can an HTTP monitor validate?

```yaml
heartbeat.monitors:

- type: http
  enabled: true
  id: elastic-co-web
  name: "elastic_corporate"
  urls: ["https://www.elastic.co/"]
  schedule: "@every 30s"
  check.response:
    status: 200          # expected status code
    body: "(?i)search"   # expected text in response (case-insensitive regex)
```

**What it validates**

1. **Status code** → expected `200`; app returns `500` → monitor **failed**.
2. **Response body** → expected text (e.g. `"search"`) must be present.
3. **SSL/TLS** → HTTPS endpoint + certificate information.

- Secured endpoint (e.g. Elasticsearch) → add `username` / `password`.

## 3. Data Stream vs Traditional Index

<a id="q9"></a>

### Q9. What are the two ways Elasticsearch stores data? Difference between Traditional Index and Data Stream?

- **Traditional Index** → like a normal DB table; documents can be **updated / deleted**.
- **Data Stream** → for **time-series data** (logs, metrics); stored in multiple **hidden backing indices**.

| Traditional Index | Data Stream |
| --- | --- |
| Normal / static data | Time-series data |
| Documents can be updated/deleted | Mainly append-only |
| Single index structure | Multiple backing indices |
| Rollover manual / alias based | Automatic rollover |
| Good for products / profiles | Good for logs / metrics |

## 4. Heartbeat Dashboard / Business Analysis

<a id="q10"></a>

### Q10. What important fields can we use for Heartbeat dashboards?

| Category | Fields | Used for |
| --- | --- | --- |
| **Monitoring info** | `@timestamp`, `monitor.name`, `monitor.type`, `monitor.id`, `url.full` | Identify monitor, filter data |
| **Status & availability** | `monitor.status`, `summary.up`, `summary.down`, `state.status`, `http.response.status_code` | Uptime, downtime, error rate |
| **Performance** | `monitor.duration.us`, `http.rtt.total.us`, `tcp.rtt.connect.us`, `tls.rtt.handshake.us` | Response time, latency |
| **Network** | `resolve.ip`, `monitor.ip`, `observer.hostname` | IP, monitoring location, observer |
| **TLS / security** | `tls.established`, `tls.version`, `tls.server.x509.not_after` | TLS connections, certificate expiry |

### Q11. What dashboards can we create using Heartbeat data?

| Dashboard | How | Example |
| --- | --- | --- |
| **Global Uptime SLA** | Up/down info → overall uptime % | `Uptime = 99.9%` |
| **Response Time Trend** | X-axis → `@timestamp`, Y-axis → `monitor.duration.us` | Latency over time |
| **HTTP Status Distribution** | Terms on `http.response.status_code` | `200` OK, `404` Not Found, `500` Server Error |
| **SSL Certificate Expiry** | `tls.server.x509.not_after` − now | `elastic.co certificate → 45 days remaining` |
