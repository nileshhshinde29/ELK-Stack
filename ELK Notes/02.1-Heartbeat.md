# Elastic Heartbeat – Uptime Monitoring

## Overview

### Q1. What is Elastic Heartbeat?

it is **lightweight monitoring tool** used to check whether a service, application, API, or server is available or not.

It continuously checks the target and sends information like **availability, response time, and status** to Elasticsearch.

We can then see this information in the **Kibana Uptime application**.

---

### Q2. What does Heartbeat allow us to do?

Heartbeat allows us to monitor:

* Applications
* APIs
* Websites
* Servers
* Network services

We can run these checks from different locations and detect problems **before users report them**.

---

# Reactive vs Proactive Monitoring

### Q3. What are the problems with Reactive Monitoring?

In reactive monitoring, we normally know about the problem **after it has already happened**.

Some problems are:

* We get alerts only after the service goes down.
* It can increase **MTTR (Mean Time to Recovery)**.
* We may not know if the problem is affecting users from another location.
* Manual health checks take time.
* We don't always have real-time visibility into SLA/SLO.
* Sometimes customers find the issue before the support or engineering team.

---

### Q4. How is Proactive Monitoring with Heartbeat different?

With Heartbeat, we continuously check the services at a fixed interval.

For example:

```text
Every 10 seconds → Check the application
Every 30 seconds → Check the API
Every 1 minute → Check the server
```

We can monitor using:

* HTTP/HTTPS
* TCP
* ICMP

---

### Q5. What is the outcome of proactive monitoring?

The main goal is to:

* Detect problems early
* Reduce downtime
* Reduce MTTR (Mean Time to Recovery)
* Improve service availability
* Identify problems before customers report them

### Q7. What are the core capabilities of Heartbeat?

Some important capabilities are:

* We can configure monitors using YAML.
* We can define the target host or URL.
* We can define how frequently the check should run.
* We can configure HTTP headers and other options.
* We can monitor SSL/TLS certificates.
* We can add custom information like environment, location, and tags.
* Data can be sent directly to Elasticsearch.

---

### Q8. What is the key advantage of Heartbeat?

One important advantage is that Heartbeat can send monitoring data **directly to Elasticsearch**, so Logstash is not mandatory for the basic Heartbeat pipeline.

We can then use Kibana's **Uptime application** to visualize the monitoring results.

---

# Types of Monitoring

### Q10. What types of monitoring can we perform with Heartbeat?

The main types are:

**1. HTTP/HTTPS**

Used to check websites and APIs.

It can verify:

* URL availability
* HTTP status code
* Response content
* SSL/TLS

**2. TCP**

Used to check whether a particular port is accepting connections.

For example:

```text
localhost:9200
```

**3. ICMP**

Used to check basic host/network connectivity.

It can provide information about:

* Reachability
* Latency
* Packet loss

**4. TLS**

Used to monitor SSL/TLS certificates and their expiration.

---

# Heartbeat Architecture

### Q11. What is the architecture of Heartbeat?

The basic architecture is:

```text
Heartbeat
    ↓
Elasticsearch
    ↓
Kibana Uptime
    ↓
Alerts / Notifications
```

### Q12. When do we use ICMP monitoring?

ICMP is mainly used when we want to check **basic network or host availability**.

For example, if I want to check whether a server is reachable:

```text
Server → Ping → Response
```

It can help us measure:

* Network reachability
* Response time
* Packet loss

It does not check whether the actual application is working. It mainly tells us whether the host/network is reachable.

---

### Q13. What does ICMP configuration look like?

Example:

```yaml
heartbeat.monitors:

- type: icmp
  id: ping-public-dns
  name: "Public DNS"
  schedule: "@every 30s"
  hosts: ["8.8.8.8", "1.1.1.1"]
  timeout: 3s   ## how long Heartbeat should wait for a response.
  mode: any  ## At least one host should respond. if ALL => All configured hosts should respond

- type: icmp
  id: ping-internal-gw
  name: "Internal Gateway"
  schedule: "@every 15s"
  hosts: ["10.0.0.1"]
  mode: all
```

### Q15. What if ICMP monitoring doesn't work?

ICMP requires permission to create raw network sockets.

On Linux, Heartbeat may need to run with the required privileges, or we can provide the required capability.

For example:

```bash
sudo setcap cap_net_raw+eip /path/to/heartbeat
```

So if ICMP is not working, we should also check the **permissions/capabilities of the Heartbeat process**.

---

# TCP Monitoring

### Q17. What does TCP configuration look like?

Example:

```yaml
heartbeat.monitors:

- type: tcp
  enabled: true
  id: localhost_Elastic
  name: "localhost_Elastic_URL"
  hosts: ["localhost:9200"]
  schedule: "@every 2m"
  check.send: "ping\n" // Heartbeat sends ping. *The server should respond with `pong`.
  check.receive: "pong" // If the expected response is received, the check passes. If not, the check can fail.

heartbeat.monitors:

- type: http
  enabled: true
  id: elastic-co-web
  name: "elastic_corporate"
  urls: ["https://www.elastic.co/"]
  schedule: "@every 30s"
  check.response:
    status: 200
    body: "(?i)search"

**1. Status Code**
Expected → 200
If the application returns `500`, the monitor can show it as failed.
**2. Response Body**
We can check whether the expected text is present in the response.
Expected → "search"
**3. SSL/TLS**
We can monitor HTTPS endpoints and also check SSL/TLS certificate information.

- type: http
  enabled: true
  id: fleetAccent
  name: fleetAccent
  urls: ["https://fleetascents.dev.ev.cv.tatamotors/"]
  schedule: '@every 30s'

- type: http
  enabled: true
  id: localhost_elastic_website
  name: localhost_elastic_website
  urls: ["http://localhost:9200"]
  schedule: '@every 10s'
  username: 'elastic'
  password: 'Nilesh@123'

- type: icmp
  enabled: true
  id: localhost_ip
  name: localhost_ip
  hosts: ["10.163.248.70"]
  schedule: '@every 50s'

- type: icmp
  enabled: true
  id: localhost_name

- type: tcp
```

## Monitoring Requirements

### Q1. What is the main rule for Heartbeat monitoring?

The main rule is:

**Heartbeat must be able to directly reach the target system.**

If the Heartbeat server cannot reach the target's **IP, port, or website**, Heartbeat will show the monitor as **DOWN**.

---

### Q2. What does each monitor require?

Different monitors have different requirements.

**ICMP Monitor**

* The server IP should be reachable.
* Firewall should allow ICMP request and response.

**TCP Monitor**

* The server IP and port should be reachable.
* It is used to check whether a particular service is accepting connections.

For example:

```text
Database → 10.0.0.5:3306
```

**HTTP/HTTPS Monitor**

* The URL should be reachable.
* DNS should resolve the URL.
* The website/API should return a valid HTTP response within the configured timeout.

For example:

```text
https://api.app.com → HTTP 200 OK
```

# Data Stream vs Traditional Index

### Q5. What are the two ways Elasticsearch stores data?

The two common ways are:

**Traditional Index:** Works more like a normal database table. Documents can be updated and deleted.

**Data Stream:** Mainly used for **time-series data** like logs and metrics. Data is stored in multiple hidden backing indices.

---

### Q6. What is the difference between Traditional Index and Data Stream?

| Traditional Index                      | Data Stream                      |
| -------------------------------------- | -------------------------------- |
| Used for normal/static data            | Used mainly for time-series data |
| Documents can be updated/deleted       | Mainly append-only               |
| Single index structure                 | Uses multiple backing indices    |
| Rollover is usually manual/alias based | Can use automatic rollover       |
| Good for products/profiles             | Good for logs/metrics            |

---

### Replica Shards

### Q8. What are Replica Shards?

Replica shards are **copies of primary shards**.

They are mainly used for:

* Data protection
* Handling node failures
* Improving read performance

For example:

```text
Primary Shard
      ↓
Replica Shard
```

The replica contains the same data as the primary.

---

### Q9. What is the Node Separation Rule?

A replica should not be placed on the **same node as its primary shard**.

For example:

```text
Node 1 → Primary
Node 2 → Replica
```

This is important because if Node 1 fails, the replica on Node 2 is still available.

---

### Q10. What is Automatic Failover?

If the node containing a primary shard fails, Elasticsearch can **promote an available replica to become the new primary**.

For example:

```text
Before:

Node 1 → Primary
Node 2 → Replica

Node 1 fails

After:

Node 2 → New Primary
```

This allows Elasticsearch to continue serving data.

---

### Q11. How do replicas improve read performance?

Search requests can be distributed between **primary and replica shards**.

So if we have more replicas, Elasticsearch has more shard copies available to handle search requests.

This can help when the cluster has a **high search/query load**.

---

# Shards

### Q13. What is a Shard?

A shard is basically a **small, independent part of an Elasticsearch index**.

Elasticsearch uses shards to split a large amount of data into smaller parts.

For example:

```text
1 TB Index
     ↓
Shard 0
Shard 1
Shard 2
```

Each shard contains part of the index's data.

---

### Q14. What is Horizontal Scaling?

Horizontal scaling means **adding more machines/nodes** instead of making one machine more powerful.

For example, instead of keeping a 1 TB index on one node:

```text
Node 1 → 1 TB
```

we can distribute the data:

```text
Shard 0 → ~333 GB
Shard 1 → ~333 GB
Shard 2 → ~334 GB
```

This allows the workload to be distributed across multiple nodes.

---

### Q15. What is Parallel Processing?

Because an index is divided into shards, Elasticsearch can process a search across multiple shards **at the same time**.

For example:

```text
Search Request
      ↓
Shard 0 ──┐
Shard 1 ──┼──> Results
Shard 2 ──┘
```

The shards process the request in parallel and Elasticsearch combines the results.

# Q19. What are common causes of Yellow status?

Common reasons include:

* Only one node is available for the required replicas.
* Shard allocation is disabled.
* There are not enough nodes for the configured replicas.
* Index allocation settings don't match available nodes.
* Disk space watermark has been reached.
* Temporary network communication problems.
* A node is restarting or recovering.

---

### Q20. What are common causes of Red status?

Common reasons include:

* Node failure
* JVM Out Of Memory
* Disk is completely full
* Network/split-brain type cluster problems
* Corrupted shards
* Missing data files
* Hardware failure

---

### Yellow and Red Cluster Issues

### Q22. Explain Yellow cluster issues in simple words.

**Single-node cluster:** You have only one node, but Elasticsearch expects a replica on another node. Since there is no second node, the replica cannot be allocated.

**Shard allocation disabled:** Shard allocation has been disabled, so Elasticsearch cannot assign the shard.

**Insufficient nodes:** You have configured more replicas than the available nodes can support.

**Index settings mismatch:** The allocation rules don't match any available node.

**Disk space watermark:** Elasticsearch detects that disk usage is too high and can stop allocating shards to that node.

**Network partition:** Nodes temporarily cannot communicate with each other properly.

**Node restart/recovery:** A node is restarting or recovering its data, so Elasticsearch waits before completing shard allocation.

---

### Q23. Explain Red cluster issues in simple words.

**Node crash:** A node containing important shard data goes offline.

**JVM OOM:** Elasticsearch runs out of JVM memory and may crash or stop processing normally.

**Disk full:** There is no available disk space, so Elasticsearch cannot properly store or update data.

**Split-brain/network issue:** Different parts of the cluster may temporarily lose communication, creating cluster coordination problems.

**Corrupted shards:** The shard data is damaged and Elasticsearch cannot properly read it.

**Missing data files:** Elasticsearch expects certain data files, but those files are missing from disk.

**Hardware failure:** Problems with the disk, RAM, CPU, or other hardware can make the node unavailable.

---

# Heartbeat Dashboard / Business Analysis

### Q25. What important fields can we use for Heartbeat dashboards?

Some useful fields are:

### 1. Monitoring Information

```text
@timestamp
monitor.name
monitor.type
monitor.id
url.full
```

These help us identify the monitor and filter the data.

### 2. Status and Availability

```text
monitor.status
summary.up
summary.down
state.status
http.response.status_code
```

These fields help us calculate **uptime, downtime, and error rates**.

### 3. Performance

```text
monitor.duration.us
http.rtt.total.us
tcp.rtt.connect.us
tls.rtt.handshake.us
```

These fields help us understand **response time and latency**.

### 4. Network Information

```text
resolve.ip
monitor.ip
observer.hostname
```

These can help us identify the IP, monitoring location, and observer.

### 5. TLS / Security

```text
tls.established
tls.version
tls.server.x509.not_after
```

These fields help us monitor TLS connections and certificate expiration.

---

### Q26. What dashboards can we create using Heartbeat data?

We can create different useful visualizations.

### Global Uptime SLA

We can use the monitor's up/down information to calculate the **overall uptime percentage**.

Example:

```text
Uptime = 99.9%
```

### Response Time Trend

We can create a time-based chart using:

```text
X-axis → @timestamp
Y-axis → monitor.duration.us
```

This shows how response time changes over time.

### HTTP Status Distribution

We can visualize HTTP status codes such as:

```text
200 → Successful
404 → Not Found
500 → Server Error
```

This helps us understand the type of HTTP responses we are receiving.

### SSL Certificate Expiry

We can track the certificate expiration date using:

```text
tls.server.x509.not_after
```

For example:

```text
elastic.co certificate → 45 days remaining
```

This helps us identify certificates that are going to expire soon.
